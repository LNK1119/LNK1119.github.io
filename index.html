코드 분석 · 다이어그램으로 구조화

QNX 환경에서 차량 업데이트 SW를 빌드하고, PlantUML 시퀀스·클래스 다이어그램을 성공 흐름부터 단계별 실패까지 점점 깊게 그리며 분석했습니다. 그 결과 업데이트 단계마다 봐야 할 클래스를 빠르게 찾게 되었고, 코드에 쓰인 스레드·파일 입출력은 C++ 예제로 직접 구현하고, GDBus 통신은 호출 흐름을 다이어그램으로 따라가며 익혔습니다.

로그 분석 · 원인을 코드 단위로

매일 정상 로그를 분석하고, Jira로 공유된 실패 이슈의 로그를 다운로드 받아 정상 로그와 비교해 원인을 찾고, 수정된 패키지는 반복 테스트와 의도적인 오류 발생으로 롤백까지 확인했습니다.

정상 로그 정리→실패 로그 비교→출력 코드 매칭→원인 파악→반복·롤백 테스트

코드 강건화 · 예외 처리 추가

파일 처리는 open, write, flush, close 단계마다 스트림 상태를 확인해 저장 실패 시 다음 단계로 넘어가지 않도록 했고, 공유 자원은 atomic과 mutex로 보호해 경쟁 상태를 막았습니다. 이 코드는 리뷰를 통과해 반영되었습니다.

open → is_open()·write → fail()/bad()·flush → 상태 확인·close → fail()

리뷰에서 배운 점 flush는 데이터를 OS 버퍼까지만 넘기므로, 전원 차단에도 기록을 보장하려면 POSIX 수준의 open·write·fsync·close가 필요합니다. 업데이트처럼 저장 신뢰성이 중요한 지점은 이 방식으로 보강해야 한다는 것을 배웠습니다.

검증 · 패키징 개선

매일 새 업데이트 패키지를 테스트해 팝업 미표시, 재부팅 후 부팅 실패, 완료 팝업 누락을 찾아 공유했고, Shell Script 패키징의 하드코딩된 향지·차종 목록을 동적으로 관리하도록 바꿨습니다.
